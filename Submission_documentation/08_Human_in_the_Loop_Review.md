# 08 — Human-in-the-Loop (HITL) Review

## 1. Overview

NetSage AI mandates human review of every AI-generated remediation proposal.
No diagnosis can result in configuration changes without explicit engineer action.

The HITL gate is implemented in src/app.py at lines 274-335.
Three decision buttons are available. One of the three must be pressed to
record the engineer's decision in the audit log.

---

## 2. The Three HITL Actions

### Action 1: Approve & Deploy (Manual)

When to use:
  The engineer reviews the AI diagnosis, agrees with the root cause, reviews the
  proposed fix_steps, and decides the commands are correct and safe to apply.

Technical enforcement:
  The button uses Streamlit's disabled= parameter:
    approve = st.button("Approve & Deploy (Manual)", disabled=not approval_allowed)

  approval_allowed is True ONLY IF:
    - confidence >= 0.75 (LLM path), OR confidence == 1.0 (deterministic path)
    - AND safety.py found no blocked commands in fix_steps

  If either condition fails, the button is greyed out and physically un-clickable.

What happens when clicked:
  append_audit_entry(case_id, "Approve & Deploy (Manual)", root_cause, engineer_note)

What does NOT happen:
  NetSage AI does NOT execute any commands on any network device.
  The engineer must manually enter the approved commands in Cisco Packet Tracer.

---

### Action 2: Edit Commands

When to use:
  The AI diagnosis is partially correct but the proposed commands are wrong,
  incomplete, or need correction. The engineer modifies the commands before approving.

Technical implementation:
  Clicking Edit sets st.session_state["editing"] = True
  A text area appears pre-populated with the current fix_steps
  The engineer modifies the commands
  A text input field allows the engineer to record the reason for the edit

Safety re-check on edited commands:
  Before saving, validate_commands() is called on the edited command list.
  If a blocked command (e.g. reload) is found in the edit:
    st.error() is displayed
    The audit entry is NOT written
    The engineer must remove the blocked command to proceed

What happens when "Confirm Edited Commands" is clicked:
  append_audit_entry(
    case_id,
    "Edit Commands",
    root_cause,
    engineer_note=f"Override: {reason} | Commands: {edited_commands}"
  )

This action documents what the AI proposed and what the engineer actually approved.
---

### Action 3: Reject

When to use:
  The AI diagnosis is incorrect (false positive). The engineer rejects the proposal
  and records the actual root cause or the reason the AI was wrong.

Technical implementation:
  Clicking Reject reveals a text input for the engineer to enter their reasoning.
  Clicking "Confirm Rejection" writes the audit entry.

What happens when confirmed:
  append_audit_entry(case_id, "Reject", ai_root_cause, reason)

The rejected AI root cause is still recorded so analysts can review it later.

## 3. Audit Log Format

Every HITL decision is appended to docs/model_audit_log.md as a markdown table row:

  | Timestamp (UTC) | Case ID | Action | Root Cause | Engineer Note |
  |---|---|---|---|---|
  | 2026-08-23 18:15 UTC | NET-001 | Approve & Deploy (Manual) | Interface GigabitEthernet0/0.30 is administratively shut down. | Verified in Packet Tracer: no shutdown restored VLAN 30 connectivity. |

Pipe characters and newlines in Root Cause and Engineer Note are escaped
to prevent table parsing errors.

The timestamp is always generated by:
  datetime.now(timezone.utc).strftime("%Y-%m-%d %H:%M UTC")

---

## 4. Dashboard Integration

The audit log is parsed by parse_audit_log() in app.py to produce:

  - Live Audit Metrics in the sidebar (total decisions, approval rate, edits, rejections)
  - HITL Decision Breakdown chart in Tab 2 (Analytics)
  - Full filterable audit table in Tab 4 (Audit Trail)

The metrics cache is cleared after every write (load_audit_metrics.clear())
so the sidebar updates immediately after each engineer decision.

## 6. Why HITL Is Genuine (Not Cosmetic)

The HITL implementation in this project is not a cosmetic checkbox. It is enforced at
multiple technical levels:

1. Approve button is PHYSICALLY DISABLED when approval_allowed == False (not just a warning)
2. Edit path BLOCKS destructive commands before writing the audit entry
3. No command execution pathway exists in the codebase (grep for subprocess, paramiko,
   netmiko, napalm — none are present or imported)
4. system_config.json has allow_direct_deployment: false
5. Every approved fix requires the engineer to type it manually into Packet Tracer
